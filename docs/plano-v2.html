Propósito deste documento

Guia de execução do Crypto Lakehouse 360, um projeto com dois objetivos: migrar a prática de um desenvolvedor ODI/Oracle para cloud com Databricks e PySpark e cobrir na prática o conteúdo da Databricks Certified Data Engineer Associate. Cada sprint diz o que construir, o que cai na prova, como aquilo era feito no ODI e como saber que está pronto.

Regra de aprendizagem: não aceitar código que você não consiga explicar. A IA explica e revisa; quem programa é você.

1. Visão do produto

Plataforma que coleta dados públicos de mercado cripto, guarda o payload original num data lake em S3, processa no Databricks em camadas Bronze, Silver e Gold, e entrega indicadores, um dashboard e um assistente que responde perguntas sobre os dados informando de quando eles são.

Entregáveis finais

  • Landing no S3 (Free Plan): payload bruto, imutável, organizado por fonte, dataset e data.
  • Catálogo crypto360 no Unity Catalog com Bronze, Silver e Gold em Delta.
  • Um pipeline declarativo (Lakeflow Spark Declarative Pipelines) com expectations e AUTO CDC.
  • Job orquestrado (Lakeflow Jobs) com agenda, parâmetros, retries, controle de fluxo e notificação.
  • Indicadores técnicos e Crypto Market Score experimental (0 a 100) com metodologia versionada e testada.
  • Dashboard AI/BI e espaço Genie restritos à Gold.
  • Repositório público com bundle, testes, CI/CD no GitHub Actions, decisões e runbook.

Escopo e limites

Projeto educacional e de portfólio. Não executa ordens, não custodia ativos, não recomenda investimento. Nenhum dado de cliente real (o Free Edition é para uso não comercial). Dados de pessoas, quando precisarmos para praticar governança, serão inventados.

3. Do ODI para o Databricks

Quase tudo o que você faz no ODI tem equivalente. O que muda é onde a lógica vive (código versionado em vez de repositório ODI) e como o motor executa (distribuído e preguiçoso em vez de SQL enviado ao Oracle).

No ODINo DatabricksDiferença que importa
Topologia: data server, schema físico e lógicoUnity Catalog: catalogo.schema.tabela, connections, external locationsO UC governa o dado em si (acesso, auditoria, linhagem), não só o metadado do ETL.
Contextos (DEV, HML, PRD)targets do bundleO mesmo código vai para cada ambiente; o que muda são variáveis por target.
LKM (carga para staging)Auto Loader, COPY INTO, Lakeflow ConnectO checkpoint lembra o que já foi lido. Acabou a tabela de controle de arquivo processado.
Tabelas C$ e I$Landing e BronzeNão são temporárias: ficam como histórico consultável e reprocessável.
IKM Incremental Update / Oracle MergeMERGE INTO ou AUTO CDC ... STORED AS SCD TYPE 1AUTO CDC trata eventos fora de ordem pelo SEQUENCE BY.
IKM Slowly Changing DimensionAUTO CDC ... STORED AS SCD TYPE 2No ODI você marcava cada coluna (add row / overwrite on change); aqui é TRACK HISTORY ON.
CKM com flow control e tabela E$Expectations (warn, drop, fail) + tabela de quarentenaA expectation com DROP só conta a linha descartada; para guardar, você cria a quarentena.
CKM static control / constraint no OracleConstraint Delta CHECK e NOT NULLViolou, a escrita inteira falha.
Journalizing (J$, consistent set)Change Data Feed, AUTO CDCSem trigger nem tabela J$: o log do Delta é a fonte das mudanças.
MappingDefinição de dataset no pipeline, ou notebook com DataFrameDeclarativo: você diz o resultado, o pipeline resolve ordem e dependências.
Package e Load PlanLakeflow Job: tarefas + DAGParalelo é o padrão quando não há dependência.
Restart do Load Plan a partir do passo com erroRepair runReexecuta só a tarefa que falhou e as dependentes.
Passo de exceção do Load PlanRun if (At least one failed, All done)A condição fica na tarefa, não num ramo separado.
Variáveis com refreshJob parameters, task values, widgetsTask value passa dado de uma tarefa para outra.
Cenário compilado e regeneradoRecurso implantado pelo bundle deployO fonte está no Git; o deploy recria o recurso a partir dele.
Smart Export/ImportGit folders + bundle + CI/CDPromoção por pull request, com testes antes de entrar.
Agente ODICompute (serverless, job cluster, SQL warehouse)Compute separado do storage: liga, processa, desliga.
OperatorHistórico de runs do Job e event log do pipelineO event log é uma tabela que você consulta com SQL.
Security ManagerGRANT/REVOKE no Unity CatalogPermissão desce na hierarquia catálogo → schema → tabela.
Partição, índice, DBMS_STATSLiquid clustering, data skipping, ANALYZE, predictive optimizationNão existe índice. A performance vem de ler menos arquivos.
FlashbackTime travel e RESTORELimitado pela retenção do VACUUM (7 dias por padrão).

Cinco mudanças de mentalidade

Hábito Oracle/ODINo Spark
Cada comando executa na horaAvaliação preguiçosa. select, filter e join só montam um plano; nada roda até uma ação (count, write, display).
O banco cuida dos arquivosArquivos Parquet imutáveis + log de transações do Delta. UPDATE reescreve arquivos; muitos arquivos pequenos deixam tudo lento.
Cursor e linha a linha em PL/SQLSempre em conjunto. collect() traz tudo para o driver e é a causa mais comum de falta de memória.
Índice resolve consulta lentaLer menos: filtrar cedo, clustering pela coluna do filtro, evitar shuffle, broadcast de tabela pequena.
Servidor ligado o tempo todoCompute por demanda. Serverless sobe em segundos e cobra só o uso; aqui ele também consome a cota diária do Free.

Regras de dados

  • Tempo: tudo em UTC. Separar open_time (tempo do evento na fonte) de _ingested_at (tempo do pipeline).
  • Unidade do timestamp: a API devolve milissegundos. A Binance anunciou que os arquivos spot de data.binance.vision passaram a usar microssegundos a partir de 2025. Conferir no primeiro arquivo e tratar na Silver; é exatamente o tipo de erro que a regra de alinhamento abaixo pega.
  • Vela em formação: a última vela devolvida ainda está aberta. Gravar com is_closed = false; o AUTO CDC atualiza quando ela fechar. Indicadores e score usam só velas fechadas.
  • Tipos: preço e volume em DECIMAL(38,12) na Silver (valor financeiro exato); indicadores em DOUBLE na Gold (cálculo estatístico).
  • Lacunas: detectar com lead(open_time) e listar numa view. Nunca preencher sem avisar.

5. Plano por sprints

Cada sprint termina com: código no repositório, teste rodando, evidência em docs/evidencias/ (consulta, print ou log), decisão registrada em docs/decisions.md e respostas para as perguntas de domínio da seção 8. O prazo segue a entrega, não o calendário; ajustar à cota do Free Edition e à data da prova.

SPRINT 0 · Fundação: contas, repositório, catálogo e conectividade

Domínios: Plataforma (6%) · CI/CD (10%) · Governança (15%)

Objetivo: deixar o ambiente pronto, versionado desde o primeiro commit, e descobrir de verdade o que o Free Edition alcança.

Demandas

  • Repositório público crypto-lakehouse-360 no GitHub; clonar como Git folder no workspace.
  • AWS no Free Plan: MFA no usuário raiz, um usuário administrativo próprio, alerta no AWS Budgets em US$ 1.
  • Bucket privado na região do workspace: Block Public Access, versionamento, SSE-S3, lifecycle que apaga versões antigas após 30 dias.
  • IAM: role para o GitHub Actions via OIDC com permissão só de s3:PutObject no prefixo landing/; policy só de leitura para o Databricks.
  • Databricks CLI com perfil crypto360; databricks.yml mínimo com target dev; bundle validate e bundle deploy.
  • SQL: CREATE CATALOG crypto360, schemas da seção 4, CREATE VOLUME crypto360.landing.raw.
  • Job conectividade: faz GET em cada domínio da tabela de fontes e grava status e latência em ops.connectivity_check.
  • Testar a ponte A (storage credential + external location). Se falhar, testar B. Registrar o caminho escolhido como ADR.
Cai na prova. Control plane fica na conta da Databricks; compute clássico fica na sua conta de nuvem; serverless fica na conta da Databricks. Tipos de compute: all-purpose (desenvolver, cobra ocioso), job cluster (produção barata, demora a subir), serverless (sobe em segundos), SQL warehouse (só SQL, muitos usuários). Nome em três níveis no UC. Volume gerenciado × externo. bundle validate só confere; deploy cria e não executa; run executa.
No ODI era. Montar a topologia (data servers, schemas físicos e lógicos) e os contextos. Aqui a topologia é o catálogo e os contextos são targets do bundle.

Aceite: bundle implantado pelo CLI; catálogo, schemas e volume existem; ops.connectivity_check preenchida; ponte escolhida e documentada; nenhum segredo no Git (.databrickscfg e .env no .gitignore).

SPRINT 1 · Coletor REST e Landing no S3

Domínios: Ingestão (21%) · Troubleshooting (10%)

Objetivo: trazer as velas da Binance para o S3 sem perder nada e sem duplicar efeito ao reexecutar.

Demandas

  • Módulo src/crypto360/ingest/binance.py: fetch_klines(symbol, interval, start_ms, end_ms) com requests.Session, timeout, retry com backoff em 429 e 5xx, leitura do header de peso, paginação por startTime (1000 velas por chamada).
  • Gravar com Boto3 em landing/binance/klines/symbol=…/interval=1h/date=…/<run_id>.json, num envelope: fonte, endpoint, parâmetros, horário da requisição, payload. Sempre arquivo novo, nunca sobrescrever.
  • Snapshot diário de exchangeInfo para BTCUSDT e ETHUSDT (alimenta o SCD 2 do Sprint 3).
  • Backfill: ZIPs mensais de data.binance.vision, conferidos pelo .CHECKSUM (SHA-256) antes de subir.
  • GitHub Actions com schedule a cada 4h e workflow_dispatch, assumindo a role por OIDC (sem chave fixa).
  • O mesmo módulo também roda como tarefa de um Job no Databricks gravando no volume. É o cenário de prova "API sem conector" e serve de plano B.
  • Testes com moto (S3 simulado) e respostas falsas: lista vazia, 429, 500, JSON inválido, falha de upload.
Cai na prova. Qual método para cada fonte: API ou banco sem conector → REST/JDBC em notebook + Job; SaaS e bancos com CDC → conector gerenciado do Lakeflow Connect; Kafka → conector standard; arquivo único → upload manual. Padrões batch, batch incremental e streaming. Senha nunca no código: dbutils.secrets.get(scope, key). Arquivo não estruturado vai para volume.
No ODI era. Chamada de web service ou data server REST, OdiFileCopy para a área de staging e LKM File. A diferença é que aqui o arquivo bruto fica guardado para sempre.

Aceite: arquivos no S3 na estrutura combinada; reexecutar gera arquivo novo e não apaga histórico; erro HTTP registrado com run_id; testes passam sem internet.

SPRINT 2 · Bronze: três formas de carregar e a definitiva

Domínios: Ingestão (21%) · Plataforma (6%)

Objetivo: entender na prática a diferença entre os métodos de carga, que é uma das perguntas mais frequentes da prova, e montar a Bronze no pipeline declarativo.

Demandas

  • Ponte S3 → volume em funcionamento (A, B ou C).
  • Laboratório: carregar a mesma pasta em três tabelas, com CTAS + read_files, COPY INTO e Auto Loader (trigger(availableNow=True), schemaLocation, checkpointLocation). Rodar cada um duas vezes e comparar contagens.
  • Pipeline crypto360_medalhao (um só, porque o Free permite um pipeline ativo por tipo) com a streaming table bronze.binance_klines: STREAM read_files, payload como VARIANT, explode do array de velas, _metadata.file_path, current_timestamp().
  • Streaming table do histórico CSV com schema explícito.
  • Upload manual pela interface de um CSV pequeno de referência (lista de ativos acompanhados).
  • Teste de schema evolution: soltar um arquivo com um campo a mais e ver o comportamento com addNewColumns e com rescue.
Cai na prova. CTAS + read_files relê tudo; COPY INTO é idempotente (não recarrega arquivo já lido; force recarrega); Auto Loader usa checkpoint e aguenta milhões de arquivos. Directory listing × file notification. schemaEvolutionMode: addNewColumns (falha, registra, inclui ao reiniciar), rescue (vai para _rescued_data), failOnNewColumns, none. JSON como STRING (col:campo), STRUCT (col.campo), VARIANT (col:campo::tipo). explode some com array vazio; explode_outer mantém. Serverless só aceita gatilho AvailableNow/Once.
No ODI era. LKM para C$ e uma tabela de controle (ou OdiFileMove para "processados") para não ler o mesmo arquivo duas vezes. Aqui o checkpoint faz esse controle.

Aceite: tabela comparativa dos três métodos em docs/; segunda execução do pipeline não relê arquivos; contagem da Bronze bate com a soma das linhas dos arquivos; arquivo com coluna extra não quebra o pipeline.

SPRINT 3 · Silver: tipos, qualidade e AUTO CDC

Domínios: Transformação e modelagem (22%) · Ingestão (21%)

Objetivo: uma linha correta por vela, com rejeitados guardados e motivo registrado.

Demandas

  • View de limpeza: epoch → timestamp UTC, cast para DECIMAL, is_closed, união da Bronze da API com a do histórico.
  • Expectations conforme a tabela de qualidade (warn, drop, fail) e streaming table de quarentena com as condições invertidas e o motivo.
  • AUTO CDC INTO silver.klines KEYS (exchange, symbol, interval, open_time) SEQUENCE BY _ingested_at STORED AS SCD TYPE 1.
  • silver.symbols como SCD 2 a partir do exchangeInfo.
  • Comparação em notebook: o mesmo resultado com MERGE INTO ... WHEN MATCHED AND s._ingested_at > t._ingested_at. Entender por que o AUTO CDC é mais seguro com eventos fora de ordem.
  • View silver.klines_gaps com lead().
  • Funções de limpeza em src/ com teste unitário (assertDataFrameEqual).
Cai na prova. EXPECT grava e conta; ON VIOLATION DROP ROW descarta e segue; ON VIOLATION FAIL UPDATE para o pipeline; constraint CHECK faz a escrita inteira falhar. AUTO CDC com SCD 1 e SCD 2. MERGE WITH SCHEMA EVOLUTION. = NULL nunca é verdadeiro; use IS NULL. TRY_CAST devolve NULL no erro. distinct() × dropDuplicates(["chave"]). Full refresh zera e reprocessa tudo.
No ODI era. CKM com flow control e tabela E$ (expectations + quarentena), IKM Incremental Update (SCD 1) e IKM Slowly Changing Dimension (SCD 2).

Aceite: consulta de duplicidade pela chave retorna zero; vela em formação é atualizada quando fecha; quarentena com motivo; lacunas listadas; rodar duas vezes não muda contagem.

SPRINT 4 · Gold: agregações, indicadores e score

Domínios: Transformação e modelagem (22%)

Objetivo: camada de consumo confiável, com cálculos conferidos por uma segunda implementação.

Demandas

  • Materialized views 4h e 1d a partir do 1h: min_by(open, open_time), max_by(close, open_time), max(high), min(low), sum(volume), só períodos completos.
  • Window functions: retornos (lag), SMA 20/50/200 (ROWS BETWEEN 19 PRECEDING AND CURRENT ROW), volatilidade, volume relativo.
  • EMA, RSI (Wilder), MACD e ATR com groupBy("symbol", "interval").applyInPandas(...).
  • Teste: amostra conferida contra pandas puro, tolerância 1e-6.
  • Score v0 de 0 a 100 (tendência, momento, volatilidade, volume) com pesos em ops.score_methodology.
  • View gold.data_freshness.
  • Opcional: Kraken como 2ª fonte (XXBTZUSD → BTC/USD) e join com a Binance para comparar o fechamento entre exchanges.
Cai na prova. View (não guarda, recalcula a cada leitura) × materialized view (guarda, refresh incremental quando possível) × streaming table (só acrescenta) × tabela (quando o seu job grava). Tipos de join: inner, left, left_anti, cross; broadcast() evita shuffle. union casa por posição e mantém duplicatas; unionByName casa por nome; SQL UNION remove duplicatas. count("*") × count("col"); approx_count_distinct.
No ODI era. Componente Aggregate e funções analíticas do Oracle (OVER), que funcionam igual no Spark SQL. O que muda é a execução distribuída: a janela particionada por símbolo roda em paralelo.

Aceite: indicadores batem com o pandas; event log mostra refresh incremental das materialized views; metodologia do score documentada com versão.

SPRINT 5 · Lakeflow Jobs: orquestração ponta a ponta

Domínios: Lakeflow Jobs (16%) · Troubleshooting (10%)

Objetivo: rodar tudo sozinho, com falha visível e recuperação sem retrabalho. É o sprint que mais pratica questões de prova por hora de trabalho.

Demandas

  • Job crypto360_diario definido no bundle:
    • for each símbolo na ponte/coleta (concorrência até 5, limite do Free);
    • tarefa de pipeline para o refresh do medalhão;
    • tarefa SQL file (arquivo no Git) que falha se houver duplicata ou atraso;
    • if/else pelo task value novas_velas: se zero, pula o refresh do dashboard;
    • tarefa de limpeza com Run if: All done.
  • Job parameters ({{job.parameters.interval}}), retry de 2 vezes com intervalo na coleta, timeout, notificação por e-mail em falha.
  • Gatilho agendado a cada 4h; job secundário com gatilho table update em silver.klines; teste de file arrival no volume.
  • Falha forçada (parâmetro simula_falha=true), leitura do DAG e repair run.
  • ops.batch_log: run_id, tarefa, linhas, duração.
Cai na prova. Tarefa notebook precisa de compute; SQL file precisa de SQL warehouse e arquivo salvo no workspace ou Git; dashboard precisa estar publicado. Run if: All succeeded (padrão), At least one succeeded, None failed, All done, At least one failed, All failed. Job parameter vence task parameter. Task values: dbutils.jobs.taskValues.set e {{tasks.t1.values.k}}. Gatilhos: scheduled, file arrival (sem custo ocioso), table update, continuous. A primeira tarefa com falha é a causa; as seguintes aparecem como "Upstream failed".
No ODI era. Load Plan com passos serial e paralelo, restart a partir do passo com erro, variáveis com refresh e o agendador do agente.

Aceite: job roda agendado e manual; falha forçada e repair documentados com print; notificação recebida; histórico de execuções consultável.

SPRINT 6 · Governança e segurança

Domínios: Governança e segurança (15%) · fazer junto o curso oficial Getting Started with Governance

Objetivo: controlar quem vê o quê e conseguir provar isso.

Demandas

  • Ownership de cada objeto (ALTER ... OWNER TO).
  • Grupo analistas com USE CATALOG, USE SCHEMA e SELECT só na Gold; testar acesso negado à Silver; REVOKE.
  • Tabela gold.watchlist_ficticia com usuários inventados: column mask no e-mail, row filter por região e a mesma regra como política ABAC com tag governada.
  • Gerenciada × externa: DESCRIBE EXTENDED, DROP e UNDROP numa tabela de teste. Se a ponte A funcionou, criar também uma tabela externa sobre o S3.
  • Lineage no Catalog Explorer (Bronze → Gold) e consultas em system tables disponíveis (auditoria, execução de jobs, uso).
  • Secret scope para a chave da CoinGecko e para a chave de leitura do S3 (ponte B).
  • Job com run_as service principal, se o Free permitir.
Cai na prova. Gerenciada: o UC escolhe o local; DROP apaga os arquivos; UNDROP em até 7 dias. Externa: LOCATION; DROP apaga só o registro. ALTER TABLE t SET MANAGED. Permissão desce na hierarquia. Para ler: USE CATALOG + USE SCHEMA + SELECT; para gravar: MODIFY. DENY só existe no Hive metastore legado. Mask e row filter são por tabela; ABAC é uma política central por tag, que vale inclusive para tabelas futuras. Principals: usuário, grupo (recomendado), service principal (automação).
No ODI era. Security Manager, com perfis e permissões sobre objetos do repositório. No UC a permissão é sobre o dado, e vale para qualquer ferramenta que leia a tabela.

Aceite: teste de acesso negado documentado; mask e filter funcionando por grupo; print do lineage; zero segredo em notebook.

SPRINT 7 · Otimização e troubleshooting

Domínios: Troubleshooting, monitoramento e otimização (10%) · Plataforma (6%)

Objetivo: justificar o layout com números e saber recuperar a tabela de um erro.

Demandas

  • CLUSTER BY (symbol, open_time) na Silver. Calcular por que particionar por data seria um erro: 2 ativos × 24 velas = 48 linhas por dia, o que gera arquivos minúsculos.
  • DESCRIBE DETAIL (número de arquivos e tamanho) antes e depois do OPTIMIZE; conferir se predictive optimization está ativa.
  • DESCRIBE HISTORY, time travel, DELETE "acidental" e RESTORE; VACUUM sem baixar a retenção.
  • Query profile no SQL warehouse: mesma consulta com e sem filtro de símbolo, comparando arquivos lidos.
  • Gerar skew de propósito num dataset sintético (uma chave com 90% das linhas) e localizar no profile.
  • docs/runbook.md com os erros reais do projeto: cota estourada, 429, schema mismatch, conflito de escrita concorrente no Delta.
Cai na prova. Skew: uma task muito mais lenta (máximo muito acima da mediana); corrige com AQE ou broadcast em join e salting em agregação. Shuffle alto: broadcast, filtrar antes. Spill: mais partições ou mais memória. Liquid clustering troca as chaves sem reescrever e não combina com partição nem Z-ORDER. Predictive optimization só em tabelas gerenciadas do UC. OOM no driver: collect(), toPandas(). spark.sql.shuffle.partitions padrão 200.
Limite do serverless. A Spark UI clássica e a maioria das configurações spark.* não ficam disponíveis; você usa o query profile. As métricas de stage (skew, spill) você estuda pelo resumo da prova.
No ODI era. Partição e índice no Oracle, DBMS_STATS, plano de execução e Flashback.

Aceite: decisão de layout com números; RESTORE demonstrado; runbook com pelo menos cinco erros reais e como foram resolvidos.

SPRINT 8 · CI/CD e deploy

Domínios: CI/CD (10%)

Objetivo: nada vai para produção sem passar por pull request e teste.

Demandas

  • Lógica em src/crypto360/ como pacote; notebooks finos que só chamam funções.
  • pyproject.toml, pytest com SparkSession local e assertDataFrameEqual, fixtures pequenas com dados reais.
  • GitHub Actions: no PR roda ruff, pytest e bundle validate; no merge na main, bundle deploy -t prod.
  • Targets: dev (mode: development, catálogo crypto360_dev, agendas pausadas) e prod (mode: production, run_as). Variáveis por target.
  • Autenticação do CI: service principal com OAuth M2M, se o Free permitir; senão token em GitHub Secret, documentando a limitação.
  • Databricks Connect: rodar uma transformação a partir do VS Code no serverless.
Cai na prova. Variável: declara em variables, usa ${var.nome}, define por target. Precedência: --var > BUNDLE_VAR_nome > arquivo de overrides > target > default. mode: development prefixa nomes e pausa agendas; mode: production valida e pede run_as. Teste unitário (função isolada, dado sintético) × integração (componentes juntos, ambiente de teste). Git folders: branch, commit+push, pull, merge; o PR é aberto no provedor. PAT só autentica no Git; automação usa service principal.
No ODI era. Smart Export/Import entre repositórios, cenários regenerados por ambiente e contextos. Aqui é o mesmo código, targets diferentes e deploy automático.

Aceite: PR com teste quebrado fica bloqueado; deploy em prod automático pelo Action; dev e prod coexistem no mesmo workspace.

Política
